# Ledger — Project Context

Offline-first Android personal-finance app. Kotlin, Jetpack Compose, Hilt, Room, MVVM+Clean Architecture. Package `com.sherif.ledger`. Work happens on `feature/ldl-foundation`.

## Build & test

- Debug build: `./gradlew installDebug`
- Release build: `./gradlew assembleRelease` — compiles a stricter, separate task graph than debug. A change that passes `compileDebugKotlin` is not proven to pass `compileReleaseKotlin`; run both before calling something done.
- Unit tests: `./gradlew testDebugUnitTest`
- No Robolectric — unit tests are plain JVM, no Android framework classes available. Anything that must be faked in a test (notifications, `Context`, etc.) needs an interface with a real Android-backed implementation, so the fake can implement the interface without touching the framework.

## Critical gotchas (each one caused a real broken build this session)

- **Same-package top-level `private object`/`private class` name collision.** `private` on a top-level declaration restricts which *file* can reference it, but Kotlin still generates a class with that exact name in the *package's* namespace regardless. Two files in the same package declaring `private object Foo` collide — "Redeclaration" / "cannot access, it is private in file" errors that look unrelated but share this one cause. If a test double is needed in more than one file in the same package, put it in its own file without `private` (use `internal`) instead of duplicating it.
- **Expression-bodied functions (`fun x(): Y = try { ... }`) cannot contain bare `return`.** Only legal in a block body (`fun x(): Y { return try { ... } }`). This specifically broke `compileReleaseKotlin` while `compileDebugKotlin` passed — don't trust a debug-only compile as proof.
- **CRLF varies per file in this repo.** Some files have Windows line endings, some don't — it's not consistent. Match whatever the specific file already uses; don't bulk-normalize across the repo (a wildcard/timestamp-based line-ending pass will silently rewrite files that were never touched).
- **Build-variant source sets already do real work here.** `app/src/debug/` and `app/src/release/` both define their own `DebugNavGraph.kt` and `RealPipelineTracker.kt` — release's are deliberate no-op stubs so debug tooling never ships to production. Before adding a "Developer Console" feature or similar, check both source sets, not just `app/src/main`, or you'll duplicate work and get a "Conflicting overloads" compile error.
- **`git log` from WSL and PowerShell against the same checkout can disagree on paths.** Backslash paths that are correct in PowerShell resolve to nothing in WSL's git. If a git command returns suspiciously empty, check which shell it ran in before concluding the history doesn't exist.
- **A fake repository's `Flow<...> = flowOf()` (zero arguments) is a truly empty flow, not "no data yet."** `DeterministicAccountIdentityResolver` calls `accountRepository.observeAllAccounts().first()` unconditionally — `.first()` on a zero-emission flow throws `NoSuchElementException` immediately. Fakes should emit `flowOf(LedgerResult.Success(emptyList()))` or a real list, never bare `flowOf()`, for any flow something might call `.first()` on.
- **Before assuming a failing test means you broke something, check whether it ever ran before.** Every compile attempt earlier this session failed before `testDebugUnitTest` could execute anything — so failures that first appeared once compilation finally succeeded could be pre-existing and simply never run until now, not new regressions. Diff the test file and the production code it exercises against `git show a9206b5:<path>` (the original pre-session base) before assuming a change caused a failure.

## Resolved — Dashboard Total Balance sign bug (was "Open investigation")

Phase B happened: a real `ledger_diagnostic_*.zip` was analyzed (2026-07-17, device OPPO CPH2651). It showed the actual root cause was never the balance *arithmetic* — `database_health.json`'s `balance_reconstruction` check passed (independently-replayed balances matched `AccountBalanceService` exactly), and `financial_trace.json`/`ledger.log` showed the backend correctly computing net worth as **-AED 53,493.38**. The very next log line showed the Dashboard displaying `totalBalance=AED 53493.38` — same magnitude, **positive**. Root cause: `MoneyFormatter.format()` always does `abs(money.minorUnits)` (by design — safe for transaction amounts, which carry direction via a separate `isExpense`-style field). `DashboardUiState.totalBalance` (net worth) had no such companion field, so its sign vanished completely between `DashboardViewModel` and the UI — unlike the Accounts screen, which already threads an `isNegative` flag per account (`AccountUi.isNegative`, colored via `LedgerTheme.colors.negative` in `AccountsScreen.kt`).

Fixed: added `DashboardUiState.isNegativeBalance` (set from the raw signed total in `DashboardViewModel`, before `MoneyFormatter` drops the sign), consumed in `DashboardScreen.TotalBalanceSection` to color the balance red when negative, matching the existing Accounts-screen convention. Also fixed an adjacent bug in the same composable found from the same log line (`balanceChangePercentage=-81%`): the month-over-month change badge was unconditionally styled green/"positive" regardless of the string's actual sign.

Not fixed, not asked: `AccountsUiState.netWorth` has the identical missing-sign defect, but `AccountsScreen.kt` never actually renders that field (only `.sections` is consumed) — no live/visible bug there currently, so left alone. Worth the same fix if that field ever gets wired up.

The two previously-patched bugs (liability self-match double-count in `AccountBalanceService`, a `DeterministicAccountIdentityResolver` scoring bug) remain real fixes but are now understood to be secondary — the diagnostic evidence points at the display bug above as what users actually saw.

## Resolved — `openingBalance` is always zero; a bounded import window makes this visible (2026-07-17)

Real-world evidence from testing "This Month": Dashboard showed **-AED 8,030.88**; the user's actual bank balance was **+AED 4.3k**. Investigated before concluding anything — sampled ~20 of the run's 262 discarded messages directly from `ledger.log` (telecom low-balance nags, a Mashreq installment-offer promo, Kotak "account inactive" notices, AMB-shortfall notices, an Axis "credit balance" info message) — all genuinely non-transactional, none a missed real transaction. `database_health.json`'s `balance_reconstruction` check also still passed. This ruled out the filter/parser as the cause.

Root cause: every account-creation path (`DeterministicAccountIdentityResolver.kt:250`, `EnsureDefaultAccountUseCase.kt:30`) hardcodes `openingBalance = Money.zero(...)` — confirmed via grep, no exceptions. `Account.kt`'s own doc comment says the *design* assumes a real opening balance ("current balance is always derived by replaying transactions... starting from this opening value") but nothing had ever actually set it to anything but zero. This was tolerable when import was unbounded (the whole SMS history was replayed, so "zero, plus nearly everything" was roughly right); a bounded window (This Month here) breaks that assumption on purpose, since a chunk of real balance history now sits outside the window with no anchor to replace it. The math was self-consistent given the incomplete data (per `balance_reconstruction` passing) — a completeness gap, not an arithmetic bug.

**Fixed**: new `SeedOpeningBalanceUseCase` — reads the account's current *computed* balance (from `AccountBalanceService`, still the only source of balance truth), takes a user-supplied real balance, and persists `openingBalance = existingOpeningBalance + (actualBalance - computedBalance)` via `AccountRepository.updateAccount` (already existed, fully wired with an integrity-check audit log, zero callers before this — clearly built for exactly this and never used). Explicitly documented as a deliberate ONE-TIME-PER-USE exception to `Account.kt`'s "opening balance is never mutated afterward" rule. Two entry points, both calling the same use case:
1. "Confirm Starting Balance" step in `SmsOnboardingScreen`/`SmsOnboardingViewModel`, shown once after a successful scan (skippable, per-account, blank = no correction) — routes through `proceedPastImport()` so it's skipped entirely when there's nothing to confirm.
2. **Standalone, reachable anytime**: Profile → "Adjust Starting Balance" (`AdjustBalanceScreen`/`AdjustBalanceViewModel`, `LedgerRoute.AdjustBalance`). Added because the onboarding step only runs once per install — a user who already completed onboarding before this existed (or whose `isSmsImported` flag is already `true` from a prior test) can never see step 1 again without a full reinstall/data-clear. This was hit directly during testing: a rebuild-and-reinstall-over-existing-app cycle skipped onboarding entirely since the flag persisted, so the balance stayed wrong despite the fix being in place.

Shared, extracted (not duplicated) between both entry points: `core/domain/util/PlainDecimalAmount.kt` (`formatSignedPlainDecimal`/`parsePlainDecimalToMinor`) and `core/designsystem/component/LedgerAmountInputField.kt`.

Separately, the user observed transaction history appearing to start "June 26th" despite selecting "This Month" (which should mean June 17, confirmed exactly via `import_summary.json`'s `windowStartMillis` and a June 18 SMS visible in the log). This is very likely just `DashboardViewModel`'s "Recent Activity" list being capped at the 20 most recent transactions (`observeRecentTransactions(20)`) — the true import boundary is correct; June 26 is just the oldest of the visible 20, not the actual cutoff. Not fully confirmed (no per-transaction date export exists in the diagnostic bundle to prove it directly) — flagged as the likely explanation, not a fixed conclusion; not changed.

Also fixed from a real screenshot: `DashboardScreen.TotalBalanceSection`'s month-over-month change badge (`"-56%"` in the screenshot) was rendering one character per line — the balance `Text` and the badge shared a `Row` with no width floor on the badge, so a wide balance string (real device data, not short preview text) left the badge almost no room and Compose's default text wrapping stacked it vertically. Fixed by stacking the badge below the balance instead of beside it, removing the horizontal contention entirely regardless of number width.
